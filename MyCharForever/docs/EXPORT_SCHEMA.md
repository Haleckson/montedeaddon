# MyCharForever – Export-Schema (exportVersion 3)

Dieses Dokument beschreibt, was ein externes Programm lesen kann. Es muss bei **jeder Änderung am Tracking** mitgepflegt werden
(Quelle der Wahrheit im Code: `MCF.ExportSources` in `Export.lua`; Prüfung im Spiel: `/mcf exportcheck`).

> **Hinweis:** Das Exportformat ist dokumentiert, damit eigene Auswertungen der eigenen Daten möglich sind. Die Website www.mycharforever.com
> (Viewer, Gestaltung, Texte, Grafiken) ist davon unabhängig und nicht zum Nachbau oder zur Weiterverbreitung freigegeben. Wer etwas Ähnliches
> bauen oder Teile davon nutzen möchte, fragt bitte vorher: wow@cinechris.de.

## Wo liegt was?

| Datei (WTF/Account/\<ACCOUNT\>/\<Realm\>/\<Char\>/SavedVariables/MyCharForever.lua) | Zweck |
|---|---|
| `MyCharForeverExportDB` | **Export-Datenbank**: das, was ein externes Programm lesen soll. Wird beim Logout/`/reload` oder mit `/mcf export write` neu geschrieben. |
| `MyCharForeverDB` | Rohdaten des Addons (inkl. Debug). Nur als Backup gedacht, Aufbau kann sich ändern. |

Beide Variablen stehen in derselben Datei und sind Lua-Tabellen (`Name = { ... }`). Ein Parser muss nur `MyCharForeverExportDB` auslesen.
Der Text-Export im Spiel (Export-Fenster) hat dieselbe Struktur als JSON-Text.

## Kopf

```
format        "MyCharForever"
exportVersion 3            -- ändert sich nur bei inkompatiblen Änderungen
addonVersion  "0.13.0"
exportedAt    Unix-Zeit (UTC)
locale        z. B. "deDE"
journeySimplified  true/false
meta          siehe unten
maps          { [mapID] = { name = "...", parent = mapID } }
data          die eigentlichen Daten (siehe unten)
```

### meta
`name`, `realm`, `faction` ("Horde"/"Alliance"), `class` (englischer Dateiname, z. B. "WARRIOR"), `race` (Dateiname),
`utcOffset` (Sekunden: lokale Zeit minus UTC beim Export – alle Zeitstempel sind Unix-Zeit/UTC, damit lässt sich die Spielerzeit umrechnen),
`gameBuild` (TOC-Nummer), `dbVersion` (Schema der Roh-DB), `screenshotFormat` (Client-Einstellung, z. B. "jpg"; Dateien liegen in `screenshotFolder`).

### maps
Wörterbuch aller in den Daten vorkommenden `mapID`s (Name in der Spielsprache und übergeordnete Karte). Wird beim Export aus dem Client gelesen.

Fehlt eine Spiel-Funktion, fehlen die zugehörigen Felder; `/mcf trackcheck` zeigt, welche Quellen vorhanden sind. |
| `settings` | nur auf Wunsch (Experten-Export) |

Nicht exportiert: `combatDebug`, `damageMeterDebug`, `maintenance`, `gearBackfilled` (interne Markierung), `dbVersion` (steht in `meta.dbVersion`).

## journey (Route)

```
format 2
fields {"timestamp","mapID","x","y","level"}
segments  { { {t,mapID,x,y,level}, ... }, ... }   -- zusammenhängende Wegstücke
simplified true, epsilon 0.0070, originalPoints N, exportedPoints M
```
`x`,`y` sind Kartenkoordinaten 0..1 (links oben = 0,0) auf der Karte `mapID`. Ein neues Segment beginnt bei Kartenwechsel,
Pause über 15 Minuten (`exportSplitSeconds`) oder Sprung über 0,20 (`maxRunJump`). Die Linie ist mit Douglas-Peucker ausgedünnt (Abweichung bis 0,7 % der Kartengröße).

## Regeln für die Weiterentwicklung

1. Neue Tracking-Daten: Schlüssel in `MCF.ExportSources` eintragen (Gruppe oder `excluded` mit Grund), hier dokumentieren, `/mcf exportcheck` muss „vollständig“ melden.
2. Bestehende Felder werden nicht umbenannt oder entfernt. Neue Felder sind ohne Versionssprung erlaubt.
3. Nur bei inkompatibler Änderung `MCF.EXPORT_VERSION` erhöhen und unten eintragen.
4. Viewer: Jeder Datenblock, der erst ab einer bestimmten Addon-Version existiert, bekommt eine Zeile in der Tabelle `FEATURES` des Viewers (`{since:"x.y.z", name:...}`). Das ist die einzige Quelle für die Kompatibilitätsanzeige und den Hinweis „Addon veraltet“; der Viewer fragt dafür nie selbst `exp.addonVersion` ab. Neue Tracking-Daten ohne `FEATURES`-Zeile gelten als nicht fertig.
